# 자동차 게임 세부 계획과 오케스트레이션 (승인됨 2026-11-20)

> 작성일: 2026-11-20. 설계는 `docs/car/design.md`. 이 문서는 "무엇을 어떤 순서로, 누구에게, 어떻게 검수하며" 만들지를 정한다.

## 1. 역할
| 누가 | 하는 일 |
|---|---|
| 사용자 | 방향 결정, 단계마다 배포 주소에서 눈 확인, PR 병합 |
| 오케스트레이터(이 세션) | 설계·수치 결정, 작업 지시서 작성, 결과 검수(코드 읽기·테스트 실행·화면 캡처), 문서 갱신, 사용자 보고 |
| 코더(Opus 5.5 하위 에이전트) | 지시서 1장 = 작업 1개 구현 + 테스트 작성 |

## 2. 진행 규칙
1. **한 번에 한 단계**. 단계가 끝나면 배포 주소와 확인 포인트를 알리고 멈춘다.
2. 작업 지시서에는 항상 넣는다: 목표, 읽을 문서 절(예: design 6·8장), 만들 파일, 공개 함수 시그니처, 수용 기준(테스트 이름), 금지 사항(sim에서 Math.random·DOM 금지, 수치는 config에).
3. sim 작업은 **순서대로**(타입을 공유하므로). render와 ui는 sim 인터페이스가 고정된 뒤 **동시에**(작업 폴더 분리) 진행할 수 있다.
4. 코더가 끝냈다고 해도 오케스트레이터가 직접 `npm test`, `tsc`, 스모크를 돌려 확인한 것만 "확인"으로 기록한다.
5. 설계에 없는 것을 코더가 임의로 정하지 않는다. 막히면 질문으로 돌려보내고, 오케스트레이터가 정하거나 사용자에게 묻는다.
6. 커밋은 작업 단위. 버전은 `car/src/version.ts`, 이력은 `docs/car/CHANGELOG.md`.
7. 교통 게임·에어 게임 파일은 건드리지 않는다(예외: `vite.config.ts`, `package.json` 스크립트, 배포 설정에 car 추가).

## 3. 단계
재미를 일찍 확인하려고 **얇게 한 바퀴 → 살 붙이기** 순서로 간다.

### 1단계 — 한 바퀴 돌기 (0.1.0) : "차 한 대를 만들어 팔아 본다"
| 작업 | 내용 | 수용 기준 |
|---|---|---|
| C1 골격 | `car/` 폴더, vite 입력, 빈 페이지, version, 스모크 스크립트 | `/car/` 로드, 콘솔 오류 0 |
| C2 sim 기초 | types, rng, time(주·월·연), game(명령 기록·toJSON) | 결정론·저장 왕복 테스트 |
| C3 차와 개발 | 5.1~5.3, 6장(설계·시험·결함). 차체 3종·가솔린만 | 보정 목표(1970년 등급 4~5), 결함 규칙 테스트 |
| C4 판매 | 7.3 공식, 국내만, 경쟁사 3곳 고정값, 월 정산, 9.4 재무 기초·파산 | 가격↑ → 판매↓, 등급↑ → 판매↑, 파산 테스트 |
| C5 3D | 데모 `buildCar`를 TS·three 0.187로 이식, 무대, 평면 대체 | 차체 3종 캡처, 생성 30ms 이하 |
| C6 화면 | 상단바, 차고, 신차 기획, 개발 진행, 출시, 리뷰(평론가 4명), 월 보고, 저장 칸 | Playwright로 신차 1대 출시까지 |
사용자 확인: 차를 만들어 파는 한 바퀴가 재미있는가, 3D와 화면 스타일이 마음에 드는가.

### 2단계 — 차종의 일생 (0.2.0) : 페이스리프트·풀체인지
| 작업 | 내용 | 수용 기준 |
|---|---|---|
| C7 lifecycle | 8장 전부(차종·세대·판 구조, 리프트·체인지 규칙, 차종 자산, 전작 비교, 재구매, 8.6 단종·부활) | 8장 규칙별 테스트, 저장 형식 2 + 형식 1 변환 |
| C8 얼굴·차대 값 | 14장의 차대/얼굴 분리, 후보 3개 생성, 시드 재현 | 같은 시드 = 같은 모양, 리프트는 옆모습 윤곽 불변 |
| C9 화면 | **신차 기획 첫 화면의 선택(새 차종 / 다음 세대 / 페이스리프트, 설계 8.7)**, 차종 카드(수명 막대·조언·버튼), 리프트 비교 화면, 체인지 흐름, 차종 계보 | Playwright: 출시 → 리프트 → 체인지 |
| C10 봇 | 16장 균형 봇 중 방치·신중·리프트 안 함 | "리프트 안 함"이 신중보다 불리함을 수치로 확인 |
사용자 확인: 리프트·체인지가 "하고 싶은 선택"으로 느껴지는가, 세대가 바뀔 때 차 모양 변화가 보이는가.

### 3단계 — 회사 (0.3.0)
직원(채용·교육·컨디션·배치), 본사 등급, 공장(증설·라인·배분), 대출, 동시 개발. 화면: 회사 탭.

### 4단계 — 시대 (0.4.0)
연구(기술 40개), 차체 10종·동력 4종·옵션 전체, 고정 사건 13개 + 무작위 사건, 시대 스타일 4종, 궁합과 조합 노트.

### 5단계 — 세계와 경쟁 (0.5.0)
지역 4곳, 경쟁사 6곳 규칙(대응 신차·히트작·리프트 주기), 시장 지도 화면, 유행.

### 6단계 — 오래 하는 이유 (0.6.0)
시상식, 업적, 회사 칭호, 기록 화면 전체, 신문 기사 문구 확충, 소리.

### 7단계 — 다듬기 → 1.0.0
60년 봇 5종 균형 조정, 처음 하는 사람용 안내(첫 차까지 힌트), 성능(아이패드), 자동 저장, 파일 내보내기·가져오기, 도움말.

## 4. 작업 지시서 틀
```
[작업 C7] 차종의 일생(sim)
목표: design.md 8장의 규칙을 car/src/sim/lifecycle.ts에 구현한다.
먼저 읽기: docs/car/design.md 5·6·7·8장, car/src/sim/types.ts, car/src/config.ts
만들 것: lifecycle.ts, tests/lifecycle.test.ts, types.ts의 Nameplate·Generation·Edition 추가, 저장 변환
공개 함수: canFacelift(state, genId): Reason|null / startFacelift(...) / startFullChange(...) / nameplateEquity(...)
수용 기준: (테스트 이름 목록)
금지: sim에서 DOM·three·Math.random·Date 사용, 수치 하드코딩(config로), 설계에 없는 규칙 추가
끝나면 보고: 바꾼 파일, 테스트 결과 원문, 설계와 다르게 한 점, 못 한 것
```

## 5. 검수 순서(작업마다)
1. 코더 보고 읽기 → 2. diff 읽기(sim 순수성, config 사용, ID 참조) → 3. `npm test`·`npx tsc --noEmit` 직접 실행 → 4. 화면 작업이면 Playwright 캡처를 눈으로 확인 → 5. `docs/car/progress.md`에 완료·확인 방법·미확인·다음 할 일 기록 → 6. 커밋.

## 6. 예상 규모 (어림, 보장 아님)
1단계가 가장 크다(작업 6개). 2단계 4개, 3~6단계 각 3~5개, 7단계는 조정 반복. 단계마다 사용자 확인으로 멈추므로, 진행 속도는 확인 주기에 달려 있다.
